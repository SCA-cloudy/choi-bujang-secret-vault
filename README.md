# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 비로그인으로 요청해 결과를 기록합니다. 1단계는 `/data.json`의 확인 표시를 읽고, 2·3단계는 비로그인 요청의 상태 코드·오류 문구·메모 개수만 기록하며 메모 본문은 기록하지 않습니다.

## 12단계 현재 상태 (탈환 작전실을 완성합니다, 2026-10-14 저장점)

`aleph.config.json`의 `step`을 12로 올렸습니다. 배포 주소(`publicAppUrl`), 로그인 발급자(`identityProvider`), 허용 경로(`allowedRoutes` 메모 API 다섯 개), 원본 API 주소(`originalApiUrl`), `restoreRoute`는 11단계와 같고, `judgeIssuer`는 운영 측이 채운 값이라 바꾸지 않았습니다. 새 기기 경로와 `/api/ops`는 11단계의 기기 경로처럼 `allowedRoutes`에 넣지 않았습니다(넣으면 안전 정책 사본 `safe-9`와 달라져 복원 전 사본 검증이 정책 변경으로 판단함). 판정기(`src/decider.mjs`)는 바꾸지 않았고 `RULE_IDS`는 실제로 구현한 세 규칙(`device_registered`, `step_up_required`, `resource_zone`) 그대로입니다. 자기 점검(`src/attack-check.mjs`)은 12단계를 받도록 고쳤습니다. 제출 묶음이 받는 직접 점검은 최대 20개라서, 6단계의 「등록 기기 읽기 허용」과 겹치는 7단계의 정상 사건 허용 점검(`decider_normal_event_allowed`) 한 개를 빼고 **로그인 없이 `GET /api/ops`를 보내 401·403으로 거부되는지** 보는 점검 한 개(`anonymous_ops_request`)를 넣었습니다. 이 한 개는 사이트로 실제 보낸 요청의 결과이며 심판의 판정이 아닙니다. 11단계 이하의 점검 결과는 그대로입니다.

**지금 작동하는 기능(12단계):** 탈환 작전실(승인된 기기에서만 열리고, 서명한 `GET /api/ops`로 판정기·탐지·회수·복구 네 칸을 「실측」과 「미실행」으로 나눠 보여 줌), 실측 요청 표(1~12단계의 정상·금지 요청을 배포 사이트로 보내 기대·실제·요청 ID·확인 시각을 한 표로 만들고 복사), 설치·실행·중지·복구 안내와 출처 구분(아래 제작 3). 1~11단계 기능은 그대로입니다(로그인, 메모 API, 기기 승인과 요청 서명, 복구 경로, 정책 사본 되돌리기, 백업 복원 훈련).

**다시 실행하는 방법:** `node --test`(전체 146개 중 알려진 실패 `package-starter` 1개를 빼고 통과), `node --test test/ops-api.test.mjs test/app-shell.test.mjs test/r5.test.mjs`, `npm run decider:test`, `npm run detect:test`, `npm run policy:diff`, `npm run bundle`(커밋 뒤 학생 PC). 배포 사이트에서는 B로 로그인 → 「이 기기 승인 요청」 → SQL Editor에서 승인 → 「승인 상태 다시 확인」 → 작전실 → 「실측 요청 표 만들기」(표 전체는 `docs/LIVE_CHECKS.md`).

### 제작 1: 탈환 작전실 (`GET /api/ops` + 화면)

**서버 (`src/ops-api.mjs`, `api/ops.js`):** 로그인과 **승인된 기기의 서명**이 있어야 답합니다(없으면 401, 서명 없음·승인 대기·다른 경로용 서명은 403, GET 말고는 405). 요청할 때마다 서버가 그 자리에서 확인한 값만 돌려주고 칸마다 출처(`source`)를 붙입니다.

| 칸 | 서버가 하는 일 | 출처 표시 |
|---|---|---|
| 판정기 규칙 | `RULE_IDS`와, 판정기 `decide()`에 가상 요청 4건(등록 기기 평소 읽기→allow, 미등록 기기→deny, 복합 이상 접속→step_up, 구역 밖 동작인 메모 삭제→deny)을 지금 넣은 결과(제작 2에서 4번째 줄 추가) | `live_virtual` (실측, 가상 요청) |
| 탐지 사건 | `detect()`에 같은 사용자의 가상 조회 30건·121건을 지금 넣은 결과(observe / propose_revocation burst_read). 반 엔진의 **실제 접속 사건 전달·회수는 이 저장소에 연결되어 있지 않아 「미실행」** | `live_virtual` + `not_run` |
| 회수 상태 | `devices` 표에서 **내 기기만** 읽어 승인·대기·회수 개수와 가린 기기 번호 목록 | `live_db` (읽기 실패 시 `unavailable`) |
| 복구 버전 | 정책 사본(`policy/safe-policy.json`의 버전·지문·원본 커밋), 복원 훈련 기록(`policy/restore-drill.json`), `notes_backup`의 내 사본마다 해시 검사(일치/불일치) | `live_file`, `live_db` |

응답과 서버 기록에는 메모 제목·본문, 전체 기기·메모 번호, 사용자 번호, 출입증이 들어가지 않습니다(번호는 앞 4자리…뒤 4자리만). 개수는 같은 응답의 가린 기록에서 세므로 둘이 어긋날 수 없습니다.

**화면 (`public/index.html`):** 기기가 **승인된 뒤에만** 「탈환 작전실」이 보이고, 「작전실 새로고침」을 누르면 서명한 `GET /api/ops`를 보내 받은 값을 **글자 그대로**(`textContent`) 네 칸에 표시합니다. 칸마다 「실측 · …」/「미실행」/「읽기 실패」 표시가 붙고, 아래에 응답의 요청 ID와 서버 확인 시각이 나옵니다. 응답을 받지 못하면 값을 지어내지 않고 HTTP 상태만 알립니다. 화면 문구는 통과 근거가 아닙니다.

### 제작 2: 실측 요청 표 (1~12단계의 정상·금지 요청)

**누를 곳:** 로그인 → (기기 승인) → 「탈환 작전실」 아래 「실측 요청 표 만들기」. 다른 계정(A)의 메모 번호 칸은 선택이며, 비우면 그 세 줄이 「미실행」으로 남습니다. 끝나면 「표 복사」로 Markdown 표를 복사합니다.

**표의 칸:** 단계 · 구분(정상/금지) · 요청 · 기대 · 실제 · 결과 · 요청 ID · 확인 시각. 「실제」는 서버가 돌려준 상태 코드와 오류 코드 그대로이고, 「결과」는 기대와 실제 글자를 비교한 **일치 / 불일치 / 미실행** 세 가지뿐입니다(통과·성공 문구 없음). 요청 ID는 응답 헤더 `x-vercel-id`, 확인 시각은 응답 헤더 `Date` 그대로이며 없으면 「없음」입니다. 메모 제목·본문, 출입증, 전체 번호는 표에 넣지 않습니다.

**화면이 실제로 보내는 요청(배포 사이트로):** 1단계 `/aleph.json` · 3단계 로그인 없는 목록·삭제(401)와 `/data.json`(404), 로그인+서명한 목록(200) · 4단계 임시 메모 추가(201)→읽기(200)→수정(200)→주인 바꾸기 값 포함 수정(403), 없는 번호 읽기(404), (A의 번호를 넣으면) A의 메모 읽기·수정·삭제(404) → 임시 메모 삭제(200)→다시 읽기(404) · 6단계 등록하지 않은 새 기기 키로 서명(403 `DEVICE_NOT_REGISTERED`, 승인 요청은 보내지 않음) · 10단계 로그인 없는 복구(401), 사본 없는 번호 복구(404), 임시 메모 복구 미리 보기(200) · 11단계 서명 없음·다른 경로용 서명·5분 전 시각·서명 뒤 본문 바꿈(모두 403) · 12단계 `/api/ops` 서명 없음(403)·로그인 없음(401)·정상(200). 6~9단계 판정기와 9단계 탐지는 `/api/ops`가 서버에서 지금 가상 요청으로 실행한 결과를 「서버 가상 요청」으로 표시합니다.

**미실행으로 남기는 것:** 2단계 공개 흔적(`git log -S`, 내 PC 명령) · 5단계 원본 주소 직접 조회(공개 키가 필요해 화면에 넣지 않음, 콘솔과 `npm run bundle` 자기 점검) · 반 엔진의 실제 접속 사건 전달·회수(이 저장소에 연결되어 있지 않음) · **운영 41종 공격 시험(심판이 실행, 이 표는 통과 근거가 아님)**.

**부작용:** 임시 메모를 만들었다가 지웁니다(중간에 실패해도 지우는 요청을 보냄). 비공개 사본(`notes_backup`)은 추가만 되는 표라서 사본 1줄이 남고, 작전실의 사본 개수가 하나 늘어납니다.

#### 설치

1. **준비물:** Node 22 이상(`package.json`의 `engines`), Git, 본인 GitHub의 Public 저장소, Vercel 계정, Supabase 프로젝트와 시험 계정.
2. **받기:** `git clone https://github.com/sca-cloudy/choi-bujang-secret-vault.git` → `cd choi-bujang-secret-vault` → `npm install`(의존성은 `@supabase/supabase-js`, `jose` 둘뿐).
3. **환경변수:** 아래 **이름**만 Vercel 프로젝트 설정의 환경변수 비밀 입력란에 학생이 직접 넣습니다. 값은 이 저장소, 로그, 채팅, 제출 묶음 어디에도 적지 않습니다. 바꾼 뒤에는 다시 배포해야 반영됩니다. `.env`와 `.env.*`는 `.gitignore`에 있습니다.

| 이름 | 용도 | 값을 받는 곳 |
|---|---|---|
| `SUPABASE_URL` | 서버 함수가 DB를 부를 주소 | Supabase 프로젝트 설정 |
| `SUPABASE_SECRET_KEY` | **서버 전용** 키. 화면·Git·로그에 넣지 않음 | Supabase API 키 화면 |
| `SUPABASE_PUBLISHABLE_KEY` | 서버가 로그인 서버에 요청할 때만 쓰는 공개용 키 | Supabase API 키 화면 |

   빌드에는 Vercel이 제공하는 저장소 소유자·이름, 커밋 SHA, 배포 주소가 필요합니다(없으면 일반 `npm run build`가 실패하도록 시작 틀이 만들었습니다).
4. **DB:** Supabase SQL Editor에서 `supabase/002_notes_write_grants.sql` → `003_notes_rls.sql` → `004_notes_revoke_direct.sql` → `005_notes_backup.sql` → `007_devices.sql` 순서로 실행합니다(`006_verify_notes_backup.sql`은 읽기만 하는 확인용). **한계:** `public.notes` 표를 처음 만든 SQL은 이 저장소에 없습니다(2단계 때 Supabase에서 만든 것). 새 프로젝트에서 처음부터 다시 만들려면 그 표 구조를 따로 알아야 하며, 이 README로는 재현을 확인하지 못했습니다.
5. **계정:** Supabase Authentication에 시험 계정(본인용 하나, 다른 사람 자료 시험용 하나)을 만듭니다. 비밀번호는 로그인 입력란에만 넣습니다.
6. **배포:** Vercel에서 이 저장소를 연결합니다(`vercel.json`: 빌드 `npm run build`, 공개 폴더 `public`). 환경변수 3개를 넣고 배포한 뒤 `/aleph.json`의 `commit`이 방금 올린 커밋인지 봅니다. `aleph.config.json`의 `repoUrl`, `publicAppUrl`, `identityProvider`는 본인 것으로 맞추고 `judgeIssuer`는 바꾸지 않습니다.

#### 실행

- **이 컴퓨터에서(DB·배포 없이):** `node --test`(전체), `npm run decider:test`, `npm run fixture:7`, `npm run detect:test`, `npm run policy:diff`, `npm run backup:drill`, `npm run build -- --local`. 이 명령들은 **가상 요청·가상 사건 연습**이며 반 엔진의 사건 전달, 실제 접속 회수, 심판의 판정을 대신하지 않습니다.

## 11단계 현재 상태 (나만의 접속 앱을 완성합니다, 2026-10-14 저장점)

`aleph.config.json`의 `step`을 11로 올렸습니다. 배포 주소, 로그인 발급자, 원본 API 주소, `judgeIssuer`, `restoreRoute`는 10단계와 같습니다. 허용 경로(`allowedRoutes`)는 메모 API 다섯 개 그대로이고, 새 기기 경로(`POST /api/device/request`, `GET /api/device/status`)는 10단계의 복구 경로처럼 넣지 않았습니다(넣으면 안전 정책 사본 `safe-9`과 달라져 복원 전 사본 검증이 정책 변경으로 판단함). 판정기(`src/decider.mjs`)는 바꾸지 않았고 `RULE_IDS`는 구현된 세 규칙(`device_registered`, `step_up_required`, `resource_zone`) 그대로입니다. 자기 점검(`src/attack-check.mjs`)은 11단계를 받도록 고쳤습니다(처음 저장점에서 `npm run bundle`이 "이 단계의 공격 점검을 구현해 주세요"로 멈춰 첫 오류만 고침). 제출 묶음이 받는 최대 20개를 지키려고 11단계부터만 7단계의 단일 신호 허용 점검(`decider_single_signal_allowed`) 한 개를 빼고, 서버의 기기 확인 함수를 가상 요청으로 직접 부른 결과 한 개(`device_signature_tamper_denied`: 서명 없음 `DEVICE_SIGNATURE_REQUIRED`, 서명 뒤 경로 변경·본문 변경 `DEVICE_SIGNATURE_INVALID`, 올바른 서명 `allow`)를 넣었습니다. 이 한 개는 이 컴퓨터에서 함수를 부른 연습이며 사이트로 보낸 요청도 심판의 판정도 아닙니다. 10단계 이하의 점검 결과는 그대로입니다.

**지금 작동하는 기능(11단계):** 설치형 웹앱 설정(`public/manifest.webmanifest`)·오프라인 안내(`public/sw.js`, 자료를 저장하지 않음)·기기 승인 상태 표시, 기기 승인 흐름(로그인 → 꺼낼 수 없는 기기 키를 메모리에 만듦 → 「이 기기 승인 요청」으로 대기 등록 → 학생이 SQL Editor에서 승인 → 「승인 상태 다시 확인」 → 자료실 열림), 메모·복구 요청마다 기기 서명(방식·경로·시각·본문 해시)을 서버가 확인. 로그인 출입증과 기기 키는 브라우저 저장소에 넣지 않습니다(새로고침하면 다시 로그인·승인). 1~10단계 기능은 그대로입니다.

### 제작 1: 설치형 웹앱 설정과 기기 승인 상태 표시

지금 배포 중인 자료실 화면(`public/index.html`)에 설치형 웹앱 설정을 붙였습니다. 따로 설치하는 접속 프로그램은 만들지 않았습니다.

- **설정(manifest):** `public/manifest.webmanifest`. 앱 이름 「BYTE BACK 내 자료실」(짧은 이름 「내 자료실」), 시작 주소 `/`, 범위 `/`, 독립 창(`standalone`), 아이콘 `public/icon.svg`. 설명에 "앱으로 설치해도 기기 승인이 끝난 것은 아니며, 승인 여부는 서버와 판정기가 정합니다"라고 적었습니다.
- **기기 승인 상태 표시:** 화면에 「이 기기 승인 상태」 칸을 두고, 지금은 **「확인 전」**으로 보입니다. "앱으로 설치(홈 화면에 추가)해도 기기 확인이 끝난 것은 아닙니다", "이 화면의 표시나 버튼만으로 권한이 생기지 않습니다"를 함께 보이고, 설치한 앱으로 열렸는지(독립 창)도 알려 주되 그것이 승인이 아니라고 적습니다. 실제 승인 확인은 제작 2에서 서버가 합니다.
- **오프라인 안내:** `public/sw.js`. 페이지 이동 요청만 네트워크로 보내고, 네트워크가 끊겼을 때만 "오프라인입니다" 안내 화면(503)을 돌려줍니다. 자료(`/api/*`)·로그인 출입증·기기 정보는 가로채지도 저장하지도 않습니다(Cache Storage·브라우저 저장소를 쓰지 않음). `vercel.json`에 `sw.js`가 늘 새로 받아지도록 `Cache-Control: no-cache`를 더했습니다.
- **기존 보호 요청:** 로그인·메모 요청 코드는 바꾸지 않았습니다. 자료 요청은 여전히 우리 서버 함수(`/api/notes`)로만, 출입증을 붙여 보냅니다.

### 제작 2 (진행 중): 기기 승인

**1단계 기기 표:** `supabase/007_devices.sql`로 `public.devices`(기기 번호 16자리, 주인, 공개 키, 이름표, 상태 `pending`/`approved`/`revoked`, 요청·승인 시각)를 만들었습니다. 개인키는 저장하지 않습니다. 브라우저 역할에는 권한이 없고, 서버(`service_role`)는 읽기와 승인 대기 등록만 할 수 있어 서버 키로도 기기를 승인할 수 없습니다. 승인은 학생이 SQL Editor에서 직접 합니다.

**2단계 서버 (`src/device-auth.mjs`, `src/device-api.mjs`, `api/device/request.js`, `api/device/status.js`):**
- 기기 번호는 공개 키(crv, x, y)의 sha256 앞 16자리(소문자 16진수)입니다. 공개 키만 받고, 개인키(`d`)가 들어 있으면 거부합니다.
- `POST /api/device/request`: 로그인과 **그 키로 서명한 요청(키 소유 증명)**을 확인한 뒤 `devices`에 **「승인 대기」로만** 등록합니다. 이 요청으로 권한이 생기지 않고, 남이 같은 기기 번호를 등록하면 `409`입니다.
- `GET /api/device/status`: 서명한 요청으로 이 기기의 상태(`pending`/`approved`)만 알려 줍니다. 자료는 주지 않습니다.
- 메모(`/api/notes`, `/api/notes/:id`)·복구(`/api/restore`)는 로그인 확인 바로 다음에 기기 확인을 합니다. 요청 헤더 `X-Device-Id`, `X-Device-Time`(ms), `X-Device-Signature`(ECDSA P-256, base64url)에 대해 서버는 다음을 모두 확인합니다: 기기가 그 사용자의 것이고 `approved`인지, `BYTEBACK-DEVICE-V1`·방식·**경로**·시각·**본문 sha256**으로 만든 글자열의 서명이 등록된 공개 키로 맞는지, 시각이 2분 안인지, 쿼리의 `id`가 경로의 메모 번호와 같은지. 하나라도 아니면 `403`(`DEVICE_SIGNATURE_REQUIRED`, `DEVICE_SIGNATURE_INVALID`, `DEVICE_NOT_REGISTERED`, `DEVICE_NOT_APPROVED`)이고 자료를 주지 않습니다. 서버 기록에는 이유 코드만 남깁니다.

**3단계 화면 (`public/index.html`):** 로그인 출입증과 기기 키를 **화면 메모리에만** 둡니다(`localStorage`·`sessionStorage`·IndexedDB에 넣지 않고, 예전 버전이 남긴 `byteback-session`은 지움). 로그인하면 **꺼낼 수 없는** ECDSA P-256 기기 키를 만들고 상태를 묻습니다. 「이 기기 승인 요청」은 대기 등록만 하며, 화면에는 승인 버튼이 없습니다. **승인 전에는 메모 요청을 보내지 않고** 쓰기 칸과 목록을 숨기며, 승인 뒤에는 모든 메모 요청에 서명을 붙입니다. 새로고침하거나 창을 닫으면 출입증과 기기 키가 사라져 다시 로그인하고 다시 승인받아야 합니다(의도한 동작).

**승인 방법(학생이 SQL Editor에서):** `update public.devices set status = 'approved', approved_at = now() where device_id = '<화면의 기기 번호>' and status = 'pending';`

## 10단계 현재 상태 (백업에서 자료실을 되살립니다, 2026-10-14 저장점)

`aleph.config.json`의 `step`을 10으로 올렸습니다. 허용 경로(`allowedRoutes` 다섯 개), 로그인 발급자, 원본 API 주소, `judgeIssuer`는 9단계와 같고, 복구 경로는 `restoreRoute`에 `POST /api/restore`로 적었습니다. `RULE_IDS`는 판정기의 구현된 규칙 세 개(`device_registered`, `step_up_required`, `resource_zone`) 그대로이며, 정책 되돌리기·복구는 판정기 규칙이 아니라 `RULE_IDS`에 넣지 않았습니다. 자기 점검 `src/attack-check.mjs`는 10단계에서 9단계의 기록 열아홉 개를 그대로 남기고, 로그인 없이 복구 경로를 부른 결과 한 개(`anonymous_restore_request`, 없는 가짜 번호만 사용)를 더해 모두 스무 개를 기록합니다. 제출 묶음이 받는 직접 점검의 최대 개수가 스무 개라서 10단계에서는 이 한 개만 더했습니다. 이 한 개는 사이트로 실제로 보낸 요청의 결과이며 심판의 판정이 아닙니다.

**지금 작동하는 기능(10단계):** 복원 전 사본 검증 절차(`npm run backup:verify`, 복원 전에 반드시 거침), 정책 사본 차이 보기(`npm run policy:diff`, 읽기 전용), 검증한 정책 사본으로 되돌리기(`npm run policy:restore`, 미리보기 후 `--apply --confirm <지문>`), 메모 한 건 복구 경로(`POST /api/restore`, 실행 전 미리 보기 `preview`), 사전 백업 다시 읽어 검증(`supabase/006_verify_notes_backup.sql`), 백업 복원 훈련과 기록(`npm run backup:drill` → `policy/restore-drill.json`). 1~9단계 기능은 그대로입니다.

### 복원 전 사본 검증 절차 (`npm run backup:verify`)

복원은 **이 절차를 먼저 따로 통과해야만** 실행됩니다. `npm run policy:restore`는 시작할 때 이 절차(`scripts/backup-verify.mjs`의 `verifyBeforeRestore`)를 그대로 거치고, 통과하지 못하면 아무것도 하지 않고 멈춥니다. 절차만 따로 실행하려면 `npm run backup:verify`를 씁니다(파일·정책·DB를 하나도 바꾸지 않음, 실패하면 종료 코드 1).

1. **사본 읽기:** `policy/safe-policy.json`이 있는지 확인합니다. 없으면 `중단`하고 복원하지 않습니다.
2. **사본 검증:** 모양, 사본 안의 지문, 사본에 적힌 원본 커밋(침해 전 저장점 `a15d850`)을 git 기록에서 다시 읽어 계산한 지문을 대조합니다. 하나라도 다르면 `중단`합니다(`digest_mismatch`, `source_mismatch`, `source_unreadable`).
3. **사본 다시 읽기:** 사본을 한 번 더 읽어 같은 방법으로 검증하고, 지문이 처음과 같은지 확인합니다. 다르면 `중단`합니다(`reread_mismatch`).
4. **실행 전에 보여 주기:** 복원할 버전(`safe-9`, 사본 지문 앞 12자리)과 바뀔 항목(현재 시험 정책과의 차이)을 보여 줍니다.

그다음 `policy:restore`는 미리보기로 바뀔 파일·항목을 보여 주고 멈춥니다. 실제로 되돌리려면 `--apply --confirm <사본 지문 앞 12자리>`가 필요하고, **쓰기 직전에 사본을 한 번 더 읽어** 검증해 처음과 지문이 같을 때만 씁니다. 쓴 뒤에는 정책을 다시 읽어 사본과 같은지 확인하고, 다르면 모두 원래대로 돌려놓습니다. 바꾸는 곳은 정책 파일 세 곳뿐이고, 계산은 임시 폴더에서 하므로 실제 운영 정책은 건드리지 않습니다. 감사 기록은 덧붙이기만 합니다.

메모 한 건 복원(`POST /api/restore`)도 같은 순서입니다. 비공개 사본을 읽어 ID·소유자·내용 해시를 검증하고, `"preview": true`로 실행 전에 버전(`backupSha256`)과 바뀔 항목을 보여 주며, 쓰기 직전에 사본을 다시 읽어 검증합니다. 사본이 없으면 `404`, 검증 실패면 `409`로 멈추고 쓰지 않습니다. DB 사본 전체는 `supabase/006_verify_notes_backup.sql`로 다시 읽어 검증합니다.

### 안전 정책 사본 검증: 원본 커밋을 다시 읽어 대조 (제작 1·2 보완)

`policy/safe-policy.json`은 9단계 저장점(커밋 `a15d850`, 심판 100점)의 정책 사본입니다. 예전에는 사본 안에 적힌 지문(sha256)하고만 대조해서, 3차 침공처럼 **사본의 정책과 지문이 함께 바뀌면** 검증을 통과하고 그 변조된 사본으로 복원될 수 있었습니다. 이제 `policy:diff`·`policy:restore`·`backup:drill`이 쓰는 사본 검증(`scripts/policy-diff.mjs`의 `readVerifiedSnapshot`)은 다음 두 가지를 모두 통과해야 합니다.

1. 사본의 모양과 사본 안의 지문이 맞는지
2. 사본에 적힌 원본 커밋의 정책 파일(`src/decider.mjs`, `src/resources.mjs`, `aleph.config.json`)을 **git 기록에서 다시 읽어** 임시 폴더에서 정책 지문을 새로 계산했을 때 사본의 지문과 같은지

2에서 다르면 `source_mismatch`, 원본 커밋을 읽지 못하면 `source_unreadable`로 **차이 보기와 복원을 모두 멈추고 아무것도 쓰지 않습니다.** 임시 폴더에서만 계산하므로 실제 운영 정책은 건드리지 않습니다. 확인 결과(2026-10-14): 원본 커밋 `a15d850`을 다시 읽어 계산한 지문 `2756f683cac9…`가 사본의 지문과 같고, `policy:diff`는 "사본 검증: 통과 (모양·지문 일치, 원본 커밋을 다시 읽어 계산한 지문과 일치)"를 보여 줍니다. 시험 `test/policy-restore.test.mjs`에 2개를 더했습니다(정책과 지문을 함께 바꾼 사본은 차이 보기·미리보기·복원 모두 `source_mismatch`로 멈추고 정책 파일이 그대로, 원본 커밋을 못 읽으면 `source_unreadable`로 멈춤). 고치기 전 코드로 첫 시험을 돌리면 실패해, 이 빈틈이 실제로 있었음을 확인했습니다.

### 백업 복원 훈련과 기록 (`npm run backup:drill`)

깃랩 사고(2017)는 백업이 몇 달째 비어 있었는데 복원 시험을 하지 않아 아무도 몰랐던 일입니다. 그래서 사본이 **실제로 복원되는지 시험하고 그 결과를 저장소에 기록**합니다. `npm run backup:drill`은 인터넷·DB·환경변수 없이 이 저장소만으로 돌고, 실제 정책 파일과 실제 메모 DB는 건드리지 않습니다.

- **정책 사본:** `policy/safe-policy.json`을 읽어 검증하고, **한 번 더 읽어** 지문이 같은지 확인합니다. 그다음 임시 폴더에 침해를 흉내 내고(정책 3건 변경), `policy:restore`와 같은 코드로 실행 전 미리보기(복원할 버전·바뀔 파일·항목)를 본 뒤, 틀린 확인 값이면 멈추는지, 맞는 확인 값이면 사본에서 복원한 정책을 **다시 읽어** 사본과 같은지, 정책 밖 설정 값과 감사 기록 한 줄이 보존되는지 봅니다. 끝나면 이 저장소의 실제 정책이 바뀌지 않았는지 확인합니다.
- **메모 사본:** 실제 복구 코드(`src/notes-restore.mjs`)를 메모리 저장소로 돌립니다. 시험 계정 B 메모를 만들 때 생긴 사본을 **다시 읽어** ID·소유자·내용 해시를 검증하고, 변조 → 미리 보기(복원할 버전·바뀔 항목) → 복원 → 다시 읽어 대조, 삭제 → 되살리기를 봅니다. 남의 요청(404), 사본 변조(409), 사본 없음(404), 로그인 없음(401)이면 멈추고 아무것도 바꾸지 않는지도 봅니다.
- **기록:** 결과는 `policy/restore-drill.json`의 `runs` 끝에 한 건씩 **덧붙이고 이전 기록은 지우지 않습니다.** 항목별 통과 여부와 짧은 설명만 담고, 메모 내용·키·사용자 정보는 담지 않습니다. 한 항목이라도 실패하면 명령이 실패(종료 코드 1)로 끝나고, 그 실패도 그대로 기록합니다. 실행만 보고 기록을 남기지 않으려면 `npm run backup:drill -- --no-write`.
- **시험:** `node --test test/restore-drill.test.mjs` 3개(정상 통과, 사본이 변조되면 실패로 기록하고 복원을 시도하지 않음, 기록은 덧붙이기만 하고 메모 내용을 담지 않음).

### 복구 경로와 비공개 사본 (제작 1~3)

**서비스·경로:** 서비스는 메모 서버 함수(Vercel `api/`)이고 복구 경로는 `POST /api/restore`입니다. `aleph.config.json`의 `restoreRoute`에 같은 값을 적었습니다. `allowedRoutes` 다섯 경로, `step`, 판정기는 이번 제작에서 바꾸지 않았습니다. 판정기는 이 경로를 따로 평가하지 않고, 알 수 없는 경로는 거부하는 기본 규칙 그대로입니다.

**요청:** `Authorization: Bearer <로그인 출입증>` 헤더와 본문 `{"id": "<메모 ID>"}` 하나를 받고, 쓰지 않고 먼저 보려면 `"preview": true`를 더할 수 있습니다(`false`는 실제 복구와 같습니다). 심판 쪽 요청 형식 문서는 없어서 이 형식은 이 저장소에서 정한 것입니다. 소유자·role 같은 값, 헤더·쿼리의 다른 표시는 읽지 않습니다.

**미리 보기(실행 전 보여 주기):** `"preview": true`이면 로그인·소유자·사본 검증(ID·소유자·내용 해시)을 실제 복구와 똑같이 거친 뒤 **아무것도 쓰지 않고** `200 {"id", "preview": true, "action": "update"|"recreate"|"none", "backupSha256", "currentSha256", "changes": {"title", "content"}}`만 알려 줍니다. 복원할 버전은 사본 해시(`backupSha256`)이고, 바뀔 항목은 `action`(있던 메모를 되돌림 / 지운 메모를 다시 만듦 / 이미 같아서 바꿀 것 없음)과 `changes`입니다. 메모 제목·본문은 응답에 싣지 않습니다. 사본이 없거나 검증에 실패하면 미리 보기도 `404`·`409`로 멈춥니다.

**응답:** 성공은 `200 {"id", "restored": "updated"|"recreated", "contentSha256"}`입니다. `401 LOGIN_REQUIRED`(로그인 없음), `405`(POST 외), `400 INVALID_RESTORE_REQUEST·INVALID_ID`(본문 모양), `403 OWNER_CHANGE_FORBIDDEN`(본문에 소유자 이름), `404 NOT_FOUND`(남의 메모·사본 없음·같은 ID가 남의 메모, 구별하지 않음), `409 BACKUP_INVALID`(사본의 내용 해시가 맞지 않음), `409 RESTORE_CONFLICT`, `500 RESTORE_FAILED`(되돌린 뒤 검증 실패, 원래대로 돌려놓음)입니다.

**비공개 사본:** DB의 `notes_backup` 표입니다(`supabase/005_notes_backup.sql`, 학생이 Supabase SQL Editor에서 직접 실행). 메모를 새로 만들 때 서버가 처음 내용 한 벌을 저장하고, 그 뒤 수정·삭제와 상관없이 그대로 둡니다. 서버 키에도 읽기·추가 권한만 주어 사본을 고치거나 지울 수 없고, 브라우저 역할에는 권한이 없습니다. 사본에 메모 본문이 있으므로 공개 저장소에는 올리지 않습니다. 이미 있던 메모는 SQL이 같은 식으로 채웁니다.

**사전 백업 다시 읽어 검증:** 복구하기 전에 DB의 사본 표 전체를 다시 읽어, 각 사본의 내용에서 해시를 새로 계산해 저장된 해시와 대조합니다. 읽기 전용 쿼리 `supabase/006_verify_notes_backup.sql`(select 하나, 서버와 같은 계산식)을 Supabase SQL Editor에서 실행합니다. 2026-10-14 실행 결과는 메모 5건, 사본 11건(지운 시험 메모의 사본도 남겨 둠), 사본 없는 메모 0건, **해시가 틀린 사본 0건**, 소유자가 다른 사본 0건, 소유자 없는 사본 0건입니다. 틀린 사본이 1건이라도 있으면 그 메모는 복구하지 않습니다(복구 경로도 같은 대조에서 `409 BACKUP_INVALID`로 멈춤).

**대조와 범위:** 복구는 사본의 ID가 요청과 같고, 소유자가 서버가 확인한 로그인 사용자와 같고, 저장된 내용 해시(sha256, 제목 + 0x00 + 내용)가 사본 내용에서 다시 계산한 값과 같을 때만 합니다. 바꾸는 곳은 그 메모 한 행뿐입니다(있으면 내용을 되돌리고, 지워졌으면 같은 ID·소유자로 다시 만듭니다). 다른 메모, 사본 표, 서버 기록은 고치거나 지우지 않습니다. 되돌린 뒤 다시 읽어 ID·소유자·해시가 사본과 같은지 확인합니다.

## 9단계 현재 상태 (9단계 시점 기록, 10단계에서 이어짐, 도플갱어를 찾고 권한을 거둡니다, 2026-10-13)

`src/detect.mjs`의 탐지 함수 `detect(events)`를 채웠습니다. 판정기(`src/decider.mjs`), 자료 API, 화면, `allowedRoutes`는 이번 단계에서 바꾸지 않았고 `judgeIssuer`도 그대로입니다. `docs/DETECT_EVENTS.md`의 가상 사건 형식을 먼저 읽고 그 계약에 있는 값만 썼습니다.

**제작 1 — 입력 처리 (`readDetectionEvents`):** 사건에서 시각(`at`), 요청 종류(`method`), 가명 사용자(`identity.sub`) 세 값만 읽어 `{atMs, method, sub}`로 정리합니다. 사건에 토큰·본문·이름·헤더·기기 값 같은 다른 이름이 붙어 있어도 읽지도 복사하지도 출력하지도 않습니다. 모양이 맞지 않는 사건은 버리고 값을 채워 넣지 않으며, 배열이 아니면 사건 내용이 없는 고정 오류(`invalid_detection_events`)를 냅니다.

**제작 2 — 탐지 규칙 `burst_read`:** 같은 `identity.sub`의 `GET` 사건이 어느 10분(600초) 구간에서든 120건을 **넘을 때만** 의심으로 봅니다. 정확히 120건은 대상이 아니고, 다른 사용자의 사건은 합산하지 않으며, `GET`이 아닌 사건과 10분 밖의 사건은 같은 묶음으로 세지 않습니다. 입력 순서와 상관없이 시각으로 정렬해 세고, 지역·네트워크 같은 계약 밖 값은 읽지 않으므로 그런 값 하나만으로 확정하지 않습니다.

**제작 3 — 회수 제안:** 의심이면 별도 결과로 `{ action: 'propose_revocation', reasonCode: 'burst_read', subject }`만 돌려주고, 아니면 `{ action: 'observe' }`입니다. 여러 사용자가 동시에 넘으면 먼저 넘은 한 명만 제안합니다. 제안만 돌려주며 회수 API를 만들거나 기기 권한을 바꾸지 않았고, 이 파일은 다른 파일·네트워크에 닿지 않습니다. 접속 허용·거부 응답 형식(판정기의 다섯 항목)은 그대로입니다.

3. `npm run decider:test`를 실행해 기존 판정기 응답이 그대로인지 봅니다. 네 줄이 모두 `통과`여야 합니다.
4. `npm run bundle`을 실행합니다(사이트에 접속하는 점검이 있어 학생 PC에서 실행합니다).

## 8단계 현재 상태 (8단계 시점 기록, 9단계에서 이어짐, 자료마다 갈 수 있는 구역을 나눕니다, 2026-10-13)

자료를 종류별 "자원 ID"로 나누고, 판정기와 자료 API 두 곳에서 구역을 확인합니다. 화면(`public/`)과 `allowedRoutes`는 바꾸지 않았고, `judgeIssuer`도 그대로입니다.

**제작 1 — 자원 ID (`src/resources.mjs`):** 경로 모양(`route`)에서만 자원 ID를 정합니다. 내 메모 경로 다섯 개는 `note.own`, 강사 공지 경로는 `notice.instructor`입니다. 표에 없는 경로는 `null`이며 추측해서 채우지 않습니다. 쿼리, 요청 본문, 화면 메뉴, `role`은 읽지 않습니다. 강사 공지 경로는 아직 서비스하지 않으며 이름만 정해 두었습니다.

**제작 2 — 판정기 규칙 `resource_zone` (`src/decider.mjs`):** `RULE_IDS`는 `device_registered`, `step_up_required`, `resource_zone` 세 개이고 모두 실제로 구현했습니다. 엔진이 확인한 `deviceRegistered`, `method`, `route`, `path`만 읽습니다. 허용하는 것은 내 메모 구역의 메모 한 건 읽기(`GET /notes/:id`)와 수정(`PUT /notes/:id`)뿐입니다. 메모 전체 목록(`GET /notes`)은 여러 사람의 자료를 한꺼번에 여는 경로가 될 수 있어 열지 않습니다(첫 제출의 심판 판정 뒤 닫았습니다). 메모 추가·삭제, 강사 공지, 표에 없는 경로, 모양이 다른 경로, `:id` 자리에 기능 이름이 들어간 경로(예: `/notes/export`)는 모두 `deny`입니다. 메모 한 건이 누구의 것인지는 판정기가 아니라 자료 API가 확인합니다. 쿼리는 기능을 고르는 데 쓰지 않고, 이전 규칙(미등록 기기 거부, 복합 이상 추가 확인)은 그대로입니다. 판정기 파일은 혼자 불러도 동작하도록 표를 안에 두며, `test/decider-zone.test.mjs`가 `src/resources.mjs`와 같은 결과를 주는지 대조합니다.

**제작 3 — 자료 API (`src/notes-api.mjs`):** 저장소가 돌려준 `owner_id`를 서버가 확인한 로그인 사용자와 한 번 더 대조합니다. 어긋난 행은 응답에 담지 않고, 수정·삭제는 저장된 소유자를 먼저 확인한 뒤에만 저장소에 닿습니다. 요청 본문·쿼리·헤더의 `role`이나 강사 표시는 읽지 않습니다. 거부 사유 코드(`NOT_OWNER` 등)만 서버 기록에 남기며 사용자 ID·토큰·메모 내용은 남기지 않습니다. 응답은 그대로 `404 NOT_FOUND`입니다.

## 4단계 현재 상태 (4단계 시점 기록, 5단계에서 이어짐)

`aleph.config.json`의 `step`은 4입니다. `allowedRoutes`는 3단계와 같은 다섯 경로입니다.

**서버:** `src/notes-api.mjs`가 목록·한 건 조회·수정·삭제를 모두 "서버가 확인한 로그인 사용자의 ID와 DB의 `owner_id`가 같은 행"에만 적용합니다. 다른 사람의 메모 번호를 알아도 없는 메모와 같은 `404`를 받습니다. 수정 요청 본문에 `owner_id` 같은 주인 값이 있으면 소유자 변경 시도로 보고 `403`으로 거부합니다. 추가할 때 `owner_id`는 요청 내용이 아니라 서버가 확인한 사용자 ID로만 저장합니다. 응답 모양은 3단계와 같습니다.

**DB:** `supabase/003_notes_rls.sql`을 SQL Editor에서 실행했습니다. `notes` 테이블에만 행 단위 보안(RLS)을 켜고, `anon`·`PUBLIC` 권한을 모두 회수했으며, `authenticated`에는 SELECT·INSERT·UPDATE·DELETE만 주고 `auth.uid() = owner_id`일 때만 허용하는 정책 4개를 만들었습니다. 다른 테이블은 건드리지 않았습니다. 서버 API는 `service_role`로 접속하며 이 역할은 RLS를 건너뜁니다. 그래서 API 경로의 실제 방어는 서버 코드의 소유자 조건이고, RLS와 권한 회수는 브라우저가 Supabase 데이터 창구에 직접 요청하는 경로를 막는 두 번째 방어선입니다.

**자료:** 처음 있던 가상 메모 네 건은 계정 A 소유이고, 계정 B 소유의 시험 메모가 한 건 있습니다. 계정을 연결할 때 쓴 SQL에는 이메일이 있어 저장소에 넣지 않았습니다.

**남은 약점·한계:** 로그인해서 직접 Data API를 부르는 경로(`authenticated`)도 시험했고 남의 행은 읽히지도 바뀌지도 않았습니다. 5단계에서 다시 확인했습니다(위 "5단계 확인 결과"). 옛 공개 커밋(`7f8a314`)과 옛 배포의 메모 노출은 해소되지 않았습니다.

## 3단계 현재 상태 (3단계 시점 기록, 소유자 검사는 4단계에서 추가됨)

`aleph.config.json`의 `step`은 3입니다. `identityProvider`에는 로그인 발급자 주소(`issuer`), 공개 키 목록 주소(`jwksUrl`), `audience`만 있고 비밀 키는 없습니다. `allowedRoutes`는 실제 자료 API 다섯 경로(`GET /api/notes`, `POST /api/notes`, `GET·PUT·DELETE /api/notes/:id`)입니다. 빌드는 공개 `data.json`을 만들지 않아 `/data.json`은 404이고, `public/aleph.json`(저장소·커밋·주소·단계)을 계속 만들며, `vercel.json`은 모든 응답에 `X-Content-Type-Options: nosniff`를 붙입니다.

화면은 Supabase Auth 이메일·비밀번호 로그인과 로그아웃(공식 SDK)을 제공합니다. 화면 코드에는 (3단계 시점 기록, 5단계에서 제거됨) 프로젝트 주소와 공개용(publishable) 키만 있고, 서버 전용 키는 없습니다. 로그인한 사람은 가상 메모를 추가·수정·삭제할 수 있습니다.

서버 API는 요청의 로그인 토큰을 `src/verify-login.mjs`(코스가 준 도우미, 고치지 않음)로 검사합니다. 토큰이 없거나 위조·만료·다른 서비스용이면 자료 없이 `401`과 `{"error":"LOGIN_REQUIRED"}`로 거부합니다. 브라우저가 보낸 사용자 ID·권한 값은 쓰지 않으며, 메모를 추가할 때는 서버가 확인한 사용자 ID를 `owner_id`로 저장합니다. 목록(`GET /api/notes`)은 `{id,title,body}` 배열이고, 지운 메모의 한 건 조회는 404입니다. 실제 처리는 `src/notes-api.mjs`에 있고, `api/notes.js`와 `api/notes/[id].js`가 이를 부릅니다.

DB 쓰기 권한은 `supabase/002_notes_write_grants.sql`(서버 함수가 쓰는 `service_role`에만 추가·수정·삭제 허용)로 줍니다. Supabase SQL Editor에서 한 번 실행해야 하며, 브라우저가 쓰는 `anon`·`authenticated`에는 계속 권한이 없습니다. 환경변수를 바꾼 뒤에는 Vercel에서 다시 배포해야 반영됩니다. 테스트 계정의 비밀번호는 저장소·로그·제출 묶음에 넣지 않습니다.

**다시 실행하는 방법:** `npm run test:notes`(API 시험), `npm run test:r5`(시험), `npm run build -- --local`(로컬 화면 확인이며 배포를 증명하지 않음), `npm run bundle`(제출 묶음. 변경을 커밋한 뒤, 사이트에 접속할 수 있는 컴퓨터에서 `bundle-notes.json`을 만들어 실행). 공격 점검은 `npm run bundle`을 실행해야 기록되며, 실행 전에는 미실행입니다. 3단계 점검은 `static_data_json_read`, `anonymous_notes_list_read`, `anonymous_note_create`이고, 4단계는 여기에 로그인 없는 수정·삭제(`anonymous_note_update`, `anonymous_note_delete`, 없는 가짜 번호로만 시험)를 더했습니다. 다른 계정이 남의 메모를 읽는 시험은 로그인이 필요해 이 점검에 넣지 않았고, 아래 "4단계 확인 결과"에 직접 확인한 내용을 적었습니다.

**3단계 시점의 남은 약점:** 당시에는 소유자 검사가 없어 로그인한 사용자가 다른 사용자의 메모도 읽고 고칠 수 있었습니다. 4단계에서 서버 코드와 DB 권한으로 막았습니다(위 "4단계 현재 상태"). 옛 공개 커밋(`7f8a314`)과 옛 배포에는 메모가 남아 있으므로, 과거 노출이 해소됐다고 볼 수 없습니다.
